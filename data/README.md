# Data: история двух турбин ВЭС

Python 3.11+. История и готовые JSON используют стандартную библиотеку;
для загрузки NOAA GRIB нужен ecCodes (`data/requirements.txt`). Data готовит историю
и архивные погодные пакеты; модель мощности и агентный цикл относятся к backend.

## Быстрый запуск

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r data/requirements.txt
./data/test.sh
python3 -m data.prepare_history audit
```

Если установленный через python.org Python на macOS сообщает об отсутствии CA,
для установки используйте `python -m pip install --cert /etc/ssl/cert.pem -r data/requirements.txt`.
Загрузчик NOAA использует системный CA в таком окружении; проверка TLS не отключается.

Для сохранения нового отчёта: `--output /tmp/source-audit-new.json`.
Файл назначения не должен уже существовать. Проверенный отчёт этого запуска:
`data/reports/source_audit.json`.

## Полученные данные

Оба CSV переданы пользователем 2026-09-23. В `data/raw/*.csv.gz` сохранены исходные
байты, сжатые gzip; скачивать файлы отдельно или иметь личный аккаунт не требуется.
Имена оригиналов, размеры, SHA-256 и основание часового пояса — `data/raw/manifest.json`.
Перед обработкой CLI проверяет контрольные суммы распакованных файлов.

Оба файла фактически покрывают 11.03.2023 00:00 — 31.01.2026 23:50.

## Время и подготовка часов

Пользователь подтвердил фиксированный **GMT+5**. Конвертация использует это смещение
для всей истории, а не меняющиеся исторические правила Asia/Almaty.
Описание организатора отсутствует. Пользователь выбрал **конец интервала как
рабочее допущение**: 12:10 относится к 12:00–12:10. `timestamp_role_confirmed`
остаётся false. Загрузчик сохраняет исходную строку времени и явный параметр роли.

Команда согласованного сценария (допущение, не подтверждение организатора):

```bash
python3 -m data.prepare_history hourly \
  --as-of 2026-02-01T00:00:00+05:00 \
  --timestamp-role end \
  --output /tmp/history-end-new.json
```

Для проверки чувствительности к началу интервала используйте `--timestamp-role start` и другой output.
Без роли метки CLI завершается ошибкой. Выбранная роль и
`timestamp_role_confirmed: false` сохраняются в результате. Допущение обязательно
указывается при представлении результатов; подтверждение организатора пока ожидается.

Полный час содержит ровно шесть последовательных 10-минутных интервалов. Для ветра,
температуры и нормализованной мощности вычисляется среднее; час помечается временем
его окончания в UTC. Турбины не объединяются. Неполные часы исключаются, пропуски
не заполняются нулями или интерполяцией. Счётчик неполных часов относится к часам,
в которых было хотя бы одно доступное наблюдение; полностью пустые периоды видны в аудите.

Ни один использованный интервал не заканчивается позже `as_of`.
Строки с исходной датой начиная с 01.02.2026 исключаются из истории обучения даже
при более позднем `as_of`. Для каждого исторического запуска нужно заново задать cutoff;
результат для конца января нельзя использовать для более раннего запуска.
Время публикации измерений неизвестно: ограничение по концу интервала не доказывает
фактическую доступность телеметрии в тот момент.

Интерфейсы и поля описаны до реализации в `docs/db-schema.md`, раздел D1.
`data.history.iter_observations` поддерживает CSV и CSV.gz с колонками организатора.
`data.history.hourly_history` принимает наблюдения и явные настройки расчёта.
Существующий общий `data/audit_csv.py` остаётся для других CSV с произвольными колонками.

## Проверки

`./data/test.sh` проверяет исходные контрольные суммы и покрытие обоих реальных файлов,
GMT+5, оба варианта метки, средние значения, независимость турбин, пропущенные часы,
повторы, некорректные поля, запрет будущих/февральских строк и обязательность параметров.
Искусственные строки в unit-тестах отделены от реальных источников.
Исходники не исправляются и не перезаписываются. Для итогового артефакта CLI создаёт
новый файл, чтобы не затереть предыдущий расчёт.

## NOAA GFS: реальная архивная погода

Источник: [NOAA GFS on AWS](https://registry.opendata.aws/noaa-gfs-bdp-pds/),
публичный bucket `noaa-gfs-bdp-pds`. Ключи и аккаунты не нужны. Выбирается один
операционный выпуск, инициализированный минимум за 6 часов до `as_of`.
Для КАЖДОГО используемого индекса и GRIB-фрагмента проверяется серверный
`issued_at <= Last-Modified <= as_of`; время скачивания сегодня записывается отдельно.
По [документации S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)
Last-Modified — время создания/последнего изменения объекта, управляемое сервером.
Это свидетельство существования текущей версии; журнал исторической доступности
HTTP и точное время первоначальной публикации NOAA не восстанавливаются.

Параметры: сетка 0.5°, U/V ветра на 100 м, температура на 2 м, шаг прогноза 3 часа.
Берётся ближайшая ячейка к координатам каждой турбины. U/V/T интерполируются на
границы часа; ветер вычисляется как `hypot(U,V)`, затем среднее граничных скоростей
и температур приближает среднее за час. Результат имеет метку конца часа B1.
Исходные узлы и извлечённые значения сохранены в provenance. Грубая сетка не
разрешает различия двух близких турбин и рельеф площадки; высота ветромера неизвестна.
Это ограничения точности, а не основание подменять прогноз фактической погодой.

Готовые пакеты для backend находятся в `data/weather`. Их воспроизводимая загрузка:

```bash
python -m data.prepare_weather \
  --start-as-of 2026-01-31T19:00:00Z --days 28 \
  --horizon-hours 48 --output-dir data/weather
```

Запуски в 19:00 UTC = 00:00 следующего дня GMT+5. Первые 24 часа каждого из
28 запусков покрывают весь февраль по местному времени; второй день служит
горизонтом 48 часов и у последнего выпуска выходит в март. Готовые файлы повторный
запуск проверяет и пропускает. Для повторной загрузки с сервера задайте новый каталог.
Один выпуск занимает десятки секунд или больше в зависимости от сети; загружаются
только три поля, а не полные глобальные файлы. Сеть/отсутствующие данные дают ошибку.

`YYYYMMDDTHHMMSSZ.json` — WeatherBatch B1; `.provenance.json` — источник, диапазоны
байтов, SHA-256, ETag, серверное время и извлечённые значения. ecCodes нужен лишь
для новой загрузки/тестов декодера: backend читает готовые JSON без него.
Данные NOAA являются реальными прогнозами. Open-Meteo был проверен при поиске,
но в рабочий архив D2 не используется.

## Подключение к backend B3

Backend `52c88cb` уже подключил D1 и читает каталог готовых погодных пакетов.
После объединения веток data/backend в репозитории:

```bash
WEATHER_ARCHIVE_DIR="$PWD/data/weather" python -m backend.server
```

Запрос из другого терминала:

```bash
curl --fail-with-body http://127.0.0.1:8000/api/forecasts \
  -H 'Content-Type: application/json' \
  -d '{"as_of":"2026-01-31T19:00:00Z","horizon_hours":48,"turbine_ids":["turbine_1","turbine_2"],"timestamp_role":"end"}'
```

Модель и HTTP API принадлежат backend. Ветка data не содержит их копий.
Прямой вызов `data.weather_gfs.build_archive` позволяет агенту backend получать
новый пакет по моменту запуска; подключение этой функции к OpenAI-циклу остаётся
за владельцем backend. Проверка каталогов не означает завершённый агентный цикл.

## Февральский факт и проверка качества

Факт февраля нужен для оценки, но не для построения прогнозов. Вопрос организатору:
«Фактическая выработка 01–28.02.2026 скрыта для оценки судьями или будет отдельным
файлом? В выданных CSV последний день — 31.01.2026. Также уточните, метка времени
обозначает начало или конец 10-минутного интервала». Сообщение подготовлено, не отправлено.
До получения ответа можно сравнивать прогноз с отложенным январским фактом, ограничивая
историю строго моментом выпуска. Нельзя выдавать январскую оценку за февральскую.

Проверка реального HTTP и январских окон после объединения веток:

```bash
python -m data.check_backend --output /tmp/data-backend-check-new.json
```

Отчёт `data/reports/backend_current_integration.json`: backend f25ef67, все три
HTTP-запроса вернули 200; роль end, история ограничена моментом запуска.
LLM этим тестом не вызывается. Реальные январские оценки базовой кривой:

| Запуск UTC | Горизонт | Турбина | Часов с фактом | MAE модели | MAE среднего истории |
|---|---:|---|---:|---:|---:|
| 2026-01-15 19:00 | 24 | turbine_1 | 24 | 0.2674 | 0.3133 |
| 2026-01-23 19:00 | 48 | turbine_1 | 48 | 0.3879 | 0.3870 |
| 2026-01-23 19:00 | 48 | turbine_2 | 48 | 0.3395 | 0.3635 |

Это всего два отложенных окна, не оценка всего января или февраля. Ошибки велики;
на втором окне для turbine_1 базовая модель чуть хуже постоянного среднего.
Нужно улучшать соответствие модельного ветра площадке и модель выработки; нельзя
представлять работоспособный пайплайн как доказательство высокой точности.

## Остающиеся зависимости команды

- Получить подтверждение роли метки (пока принято end) и задержки телеметрии.
- Получить фактическую выработку февраля для проверки точности.
- Подключить автоматический сбор к OpenAI-циклу backend и провести общее демо с UI.
