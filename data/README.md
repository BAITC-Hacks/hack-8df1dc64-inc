# Data: проверка исходных данных

Первая задача — независимый аудит CSV перед согласованием общей схемы данных.
Утилита только читает файл, не очищает его, не вычисляет выработку и не вызывает backend.
Python 3.11+; сторонние зависимости и ключи не нужны.

Из корня репозитория:

```bash
./data/test.sh
python3 data/audit_csv.py /path/to/source.csv
```

Названия колонок нужно передать точно как в исходном файле. Следующий пример показывает
синтаксис, а не утверждает формат ещё не полученных данных организаторов:

```bash
python3 data/audit_csv.py /path/to/source.csv \
  --required turbine --timestamp time \
  --numeric wind --numeric power --numeric temp \
  --key turbine --key time
```

Для CSV с `;` используйте `--delimiter ';'`. По умолчанию кодировка UTF-8 с поддержкой BOM;
другая задаётся через `--encoding`. По умолчанию даты ISO 8601; иной формат задаётся явно,
например `--time-format '%d.%m.%Y %H:%M'`. Десятичный разделитель — точка.
Для нескольких обязательных или числовых колонок повторяйте соответствующий флаг.

JSON в stdout содержит количество записей, названия колонок, число пропусков и ошибок,
минимальную/максимальную дату. Дубликаты проверяются только при заданном `--key`;
несколько таких флагов формируют составной ключ. Одновременные записи разных турбин
допустимы, если идентификатор турбины входит в ключ. Даты с часовыми поясами сравниваются
в UTC. Датам без пояса пояс не назначается. Смешение дат с поясом и без него — ошибка.

Коды выхода: `0` — заданные проверки пройдены; `1` — обнаружены проблемы в записях;
`2` — файл невозможно прочитать, заголовок некорректен или аргументы неверны.
Ошибки чтения выводятся в stderr; проблемы записей — в JSON stdout.
Пропуски в необязательных колонках сообщаются, но не приводят к коду 1.
Колонки `--numeric`, `--timestamp` и `--key` автоматически проверяются на пропуски.
NaN и бесконечность не считаются допустимыми числами.

Ограничения: XLSX не поддерживается; CSV не изменяется и не агрегируется по часам.
Не проверяются физические пределы, непрерывность времени, train/test-разделение и полнота
периода ТЗ: это требует исходного датасета и согласованного контракта. Успешный аудит
не означает готовность данных для модели. Составные ключи хранятся в памяти.
Тесты используют явно синтетические временные файлы, не заменяющие данные ВЭС.

## Что нужно получить от команды

- Исходные файлы организаторов за март 2023 — январь 2026, описание колонок и единиц.
- Часовой пояс «статистического времени», частоту измерений, связь файлов с турбинами.
- Смысл нормализации мощности; допустимость отрицательных значений и пропусков.
- Заполненную `docs/db-schema.md` для следующего этапа загрузки и передачи в backend.

## Погодный архив: предварительная проверка 2026-09-23

ТЗ в `docs/task-board.md` требует прогнозов, доступных на момент исторического расчёта.
[Open-Meteo Single Runs](https://open-meteo.com/en/docs/single-runs-api) позволяет выбрать
запуск через `run`, однако инициализация предшествует публикации. Документация указывает
архив ECMWF с марта 2024, но описывает ранние данные как hindcasts. Поэтому покрытие дат
само по себе не доказывает соответствие ТЗ: происхождение конкретных запусков и время
их доступности пока не подтверждены. Запросы к погодному API в этой задаче не выполнялись.

[Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api) сшивает
первые часы разных запусков в непрерывный ряд; такой ряд сам по себе не воспроизводит
24–48-часовой прогноз, известный на выбранную дату. До проверки источника нельзя заменять
архив выданных прогнозов фактической погодой, реанализом или синтетическими значениями.
