# API-контракт

Источник истины для интерфейсов backend. Изменения: согласование → этот документ и
`docs/db-schema.md` → реализация. Версия B1 согласована пользователем 2026-09-23.

## B1 — проверка входа до расчёта прогноза

Реализация и команды проверки опубликованы в ветке `backend`, коммит `1df63a3`.
На этапе синхронизации в `main` собраны общие документы; код модулей находится в рабочих ветках.

Python-интерфейс: `backend.validation.validate_forecast_inputs(request, weather)`.
Два аргумента — словари с полями из `docs/db-schema.md`; функция не изменяет входы.
Все перечисленные поля обязательны; неизвестные поля отклоняются, чтобы опечатки не
игнорировались. Списки передаются как JSON-массивы / Python `list`.

Успех: неизменяемый объект `ValidatedForecastInput` с полями `request` и `weather`.
Все временные метки преобразованы в timezone-aware `datetime` в UTC.
`request.turbine_ids` и `weather.points` — кортежи. Точки упорядочены сначала по порядку
турбин в запросе, затем по времени. Остальные поля сохраняют смысл, определённый схемой.

Это проверка данных, а не результат расчёта мощности; B1 не вызывает погодный источник,
не обучает модель, не возвращает прогноз выработки и не выполняет агентный цикл.

B1 сам по себе не предоставляет HTTP API. Контракт следующего этапа B2/B3 зафиксирован
ниже до реализации, в рамках поручения пользователя продолжить расчёт и интеграцию.

## Ошибки B1

При некорректном входе возбуждается `ForecastValidationError` с полями `code`, `field`,
`message`; `as_dict()` возвращает словарь с этими тремя строками.

| Код | Когда |
|---|---|
| `INVALID_REQUEST` | Неверный тип, неизвестное/отсутствующее поле запроса, некорректная дата, горизонт или список турбин |
| `INVALID_WEATHER` | Неверная структура или значение погодных данных, некорректная дата, `issued_at > available_at` |
| `WEATHER_NOT_AVAILABLE` | `available_at > as_of` |
| `INCOMPLETE_WEATHER_GRID` | Пропуск, повтор, лишний час или точка для незапрошенной турбины |

`field` — путь от `request` или `weather`, например `weather.available_at` или
`weather.points[3].wind_speed_ms`. Возвращается первая обнаруженная ошибка.
Порядок: запрос → метаданные погоды → значения и принадлежность точек сетке → полнота сетки.
Тексты `message` поясняют причину; программная обработка использует `code` и `field`.

Пример представления ошибки:

```json
{
  "code": "WEATHER_NOT_AVAILABLE",
  "field": "weather.available_at",
  "message": "Weather was published after the forecast cutoff."
}
```

## Приёмка B1

- Успех на 24 часах для одной турбины и 48 часах для двух турбин.
- Одинаковые моменты с разными смещениями часового пояса сравниваются одинаково.
- Выпуск, опубликованный после момента запуска, отклоняется.
- Неполная сетка, повторные точки, неправильные типы и нечисловые значения отклоняются.
- Запуск тестов: `bash backend/test.sh` либо `python -m unittest discover -s backend/tests -t . -v`
  из корня репозитория; Python 3.10 или новее.

Искусственные данные тестов проверяют правила B1; они не доказывают точность прогноза
или наличие реального погодного архива.

## B3 — HTTP API для UI

Статус: **контракт зафиксирован, реализация в работе**. Базовый адрес разработки:
`http://127.0.0.1:8000`. Python 3.11+ (общий минимум для Backend и Data D1).
JSON UTF-8, максимальный размер тела 1 MiB. Неизвестные поля, повтор JSON-ключа и
NaN/Infinity отклоняются. Вложенный `weather` проверяется по B1.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Проверка доступности сервера |
| POST | `/api/history/summary` | Проверка реальной истории и построение базовой кривой мощности |
| POST | `/api/forecasts` | Почасовой расчёт по истории и погодному пакету |

`GET /api/health` → 200 `{"status":"ok","service":"wind-forecast-backend"}`.
Это проверка сервера, не подтверждение доступности погоды или OpenAI.

### POST /api/history/summary

```json
{
  "as_of": "2026-01-31T19:00:00Z",
  "turbine_ids": ["turbine_1", "turbine_2"],
  "timestamp_role": "start"
}
```

Все три поля обязательны. Ответ 200 — `HistorySummary` из `docs/db-schema.md`.
`timestamp_role` задаётся пользователем явно; пример `start` не подтверждает разметку
организатора. UI должен показывать, что выбор начала/конца интервала пока является допущением.

### POST /api/forecasts

```json
{
  "as_of": "2026-01-31T19:00:00Z",
  "horizon_hours": 24,
  "turbine_ids": ["turbine_1", "turbine_2"],
  "timestamp_role": "start"
}
```

Все четыре поля обязательны. Дополнительное необязательное поле `weather` принимает полный
`WeatherBatch` B1 для явной передачи готового архива/интеграционного теста. UI может его
не передавать: тогда backend читает файл из настроенного оператором `WEATHER_ARCHIVE_DIR`.
Имя файла определяется UTC-временем `as_of`: например `20260131T190000Z.json`.
Содержимое — пакет B1 с одним выпуском; из полного пакета выбираются запрошенные часы/турбины,
после чего выполняется B1. Повторные точки запрошенной сетки не удаляются и приводят к ошибке.
При отсутствии файла или настройки возвращается 503; фиктивная погода не подставляется.
Загрузка из каталога — временный транспорт реального архива, не самостоятельный сбор погоды
и не завершённый агентный цикл.

Ответ 200 — `ForecastResult` из `docs/db-schema.md`. Все даты результата UTC с Z.
Для отображения UI группирует `points` по `turbine_id`; значение графика — `normalized_power`
в исходной нормализованной шкале. Поля `warnings` показываются пользователю.
Отдельный запуск пересчитывает результат; при изменении погодного файла используется новое
содержимое. Вызовы OpenAI и автономное получение погоды добавляются отдельным этапом.

### Ошибки HTTP

Тело: `{"error":{"code":"...","field":"...","message":"..."}}`.

| HTTP | code | Причина |
|---|---|---|
| 400 | `INVALID_JSON` | Некорректное JSON-тело, повтор ключа, NaN/Infinity |
| 403 | `ORIGIN_NOT_ALLOWED` | Origin не входит в разрешённые |
| 404 | `NOT_FOUND` | Неизвестный маршрут |
| 405 | `METHOD_NOT_ALLOWED` | Неподдерживаемый метод |
| 413 | `PAYLOAD_TOO_LARGE` | Тело больше 1 MiB |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Требуется Content-Type application/json |
| 422 | Коды B1, `INVALID_HISTORY`, `INSUFFICIENT_HISTORY` | Ошибка параметров, погоды, истории или недостаточная история |
| 503 | `HISTORY_UNAVAILABLE`, `WEATHER_UNAVAILABLE` | Отсутствует источник истории или погодный пакет |
| 500 | `INTERNAL_ERROR` | Непредвиденная ошибка сервера; детали в серверном журнале |

По умолчанию CORS разрешён для `http://127.0.0.1:3000` и `http://localhost:3000`.
Оператор задаёт список через `UI_ORIGINS` (через запятую). Поддерживается OPTIONS preflight.
HTTP работает синхронно; UI показывает ожидание ответа, не выдумывая промежуточные этапы.
