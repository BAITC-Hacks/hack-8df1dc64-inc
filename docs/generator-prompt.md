Описание задачи
Необходимо разработать Agentic AI-систему для прогнозирования почасовой выработки ветроэлектростанции (ВЭС) на горизонте 24–48 часов.

Участникам предоставляются координаты и исторические данные работы ВЭС с марта 2023 года до 31 января 2026 года включительно. 

Необходимо выполнить прогнозирование за тестовый период с 1 февраля 2026 года по 28 февраля 2026 года.

Предоставляемые данные
координаты турбины 1: https://maps.app.goo.gl/iN6svMt69D5qRpFU9
координаты турбины 2: https://maps.app.goo.gl/8UQMwsYavY6nLvFY8
статистическое время;
средняя скорость ветра, м/с;
нормализированная активная мощность на стороне линии;
средняя температура окружающей среды, °C.

Задача участников
Необходимо разработать решение, которое:
На основании предоставленных исторических данных строит модель прогнозирования почасовой выработки ВЭС.
Самостоятельно получает по координатам ВЭС из открытых источников погодные прогнозы, доступные на соответствующий момент прогнозирования.
Формирует прогноз выработки ВЭС на следующие 24–48 часов с почасовой детализацией.
Реализует процесс в формате Agentic AI, где система самостоятельно выполняет полный цикл:

получение внешних погодных данных - подготовка данных - запуск модели прогнозирования - формирование почасового прогноза - анализ результата - повторный расчёт при обновлении входных данных.

Выбор открытых источников погодных данных, ML-моделей, методов обработки данных и архитектуры AI-агента остаётся за участниками.

Участникам необходимо воспроизвести процесс, как если бы прогноз выполнялся в прошлом:
на 31 января — сформировать прогноз на следующие 24–48 часов;
на 1 февраля — сформировать новый прогноз на следующие 24–48 часов;
далее последовательно повторить прогнозирование в течение тестового периода.

Для каждого прогнозного периода участники должны использовать архивные прогнозы погоды, которые были доступны на соответствующий момент времени, а не фактические погодные значения, ставшие известными позднее.

## ЗАДАНИЕ ДЛЯ МОДЕЛИ

Ты помогаешь команде из 3 человек на хакатоне HackAlem AI (Астана, при технологическом
партнёрстве OpenAI, формат — agentic AI) подготовить рабочие документы для параллельной
разработки в оставшееся соревновательное время (5 часов). Команда использует Claude Code и/или
OpenAI Codex как AI-агентов для написания кода, каждый участник — на своём ноутбуке.

### Обязательные условия, которые нужно учитывать при генерации (кратко, по Положению)

- Каждая задача хакатона имеет собственное полноценное ТЗ со своими критериями — НЕ вставляй
  придуманные или усреднённые критерии оценки; если критерии заданы в ТЗ выше — используй их
  дословно,
  не изобретай числа.
- Есть отдельная, фиксированная для ВСЕХ задач таблица критериев Demo Day (только для
  финалистов, 100 баллов: Ценность решения 25, Результат и качество решения 20,
  Инновационность 15, Потенциал развития и масштабирования 20, Презентация/демо/ответы 20) —
  вставляй её как есть в CLAUDE.md/AGENTS.md, это не задача-специфичный критерий.
- Использование OpenAI API продуктом — не обсуждается, это дано форматом хакатона. Опиши это
  как безусловный технический факт в architecture.md/CLAUDE.md/AGENTS.md/api-contract.md, без
  оговорок и без слова «возможно».
- Логистика выдачи ключа OpenAI API участникам (сроки, лимиты) — вопрос организационный,
  может быть не до конца ясен на старте. Эта оговорка должна попасть ТОЛЬКО в
  docs/resources-needed.md, и только как пометка по логистике выдачи, а не как сомнение в
  том, нужен ли API вообще.
- Обязательное требование: команда обязана обеспечить техническим экспертам демо/тестовый
  доступ к любому используемому внешнему API/сервису без необходимости личного аккаунта
  участника — отрази это в README и resources-needed.md.
- Требование к README: описание решения и назначение, описание архитектуры, используемые
  технологии, инструкции по установке, инструкции по запуску, необходимые зависимости,
  параметры окружения, порядок проверки основного сценария работы — все эти пункты обязаны
  присутствовать явно, не общими словами.
- Критично: несоответствие требованию воспроизводимости (проект не разворачивается и не
  проверяется по инструкциям README на чистом клоне) — риск недопуска к дальнейшему отбору.
  Отрази это предупреждение явно в README.
- Разработка обязана вестись только в репозитории, созданном Организатором через
  edu.astanahub.com — не предлагай создавать отдельные репозитории.
- Отсутствие у команды подтверждённого результата за любой отчётный час соревновательной
  части — основание для дисквалификации. progress.md должен быть построен так, чтобы это
  физически было видно по часам.
- Не изобретай источники данных/API, в которых не уверен — используй предложи варианты или попроси найти вместо выдумывания.
- Разрешено заранее готовить инфраструктуру/инструменты/шаблоны, если это не готовый продукт
  и не основная часть решаемой задачи — README должен явно раскрывать, что именно было
  подготовлено заранее (этот файл-генератор, контракт CLAUDE.md/AGENTS.md, Stop-hook,
  supervisor-агент, шаблоны docs/), а что создано во время соревновательной части.

### Шаг 0 — прежде чем генерировать файлы: определи нужные внешние ресурсы

Проанализируй идею решения и ТЗ задачи и определи ВСЕ внешние данные/API/датасеты, которые
потребуются (не ограничивайся одним примером вроде погоды или спутниковых снимков — ищи то,
что реально нужно именно этой идее). Для каждого источника укажи уровень уверенности в его
существовании и доступности, и fallback на синтетические/тестовые данные, если уверенности
нет. Не изобретай источник, если не уверен — задай вопрос или предложи решения
Результат этого шага идёт в `docs/resources-needed.md`.

### Файлы для генерации (каждый — в отдельном промаркированном блоке кода)

1. `CLAUDE.md` — контракт команды для Claude Code: кейс, критерии (задача-специфичные из ТЗ +
   фиксированная таблица Demo Day), правила репозитория/почасового чекпоинта/воспроизводимости,
   что можно готовить заранее, разделение по модулям (backend+API/data/ui, с явной отсылкой,
   что оно гибкое — см. handover-protocol.md), контракт как источник истины, ссылка на
   handover-protocol.md для смены модуля, запрет имитации, правило автозаполнения progress.md,
   правило тестов этапа, Definition of Done, технический риск (не обучать ML с нуля).
2. `AGENTS.md` — то же самое для Codex, с явным указанием, что технического Stop-hook нет и
   дисциплина progress.md/тестов — полностью на самоконтроле.
3. `docs/architecture.md` — конкретный пайплайн под эту идею (входные данные → обработка →
   вызовы OpenAI API → расчёт результата → API → UI), без универсального шаблона, привязанный
   к ТЗ задачи.
4. `docs/api-contract.md` — реальные эндпоинты, схемы запроса/ответа, ошибки под эту идею.
5. `docs/db-schema.md` — реальная схема данных под эту идею, источник данных.
6. `docs/plan.md` — реальный план на 5 часов под эту идею, включая почасовой чек-поинт и
   финальную проверку воспроизводимости.
7. `docs/progress.md` — таблицы Backend(+API)/Data/UI на 5 часов, таблица «Смены модуля».
8. `README.md` — по требованиям выше, с реальным содержанием (не общими словами), с
   предупреждением про воспроизводимость и разделом демо-доступа к внешним сервисам.
9. `docs/kickoff-prompt.md` — три готовых стартовых промпта (backend+API/data/ui) под эту
   конкретную идею, с реальной первой задачей для каждого, а не плейсхолдером.
10. `docs/resources-needed.md` — результат Шага 0, с колонкой демо-доступа для экспертов.
11. `docs/task-tor.md` — вставить туда дословно полный текст ТЗ задачи и её критерии оценки
    (из раздела «ОПИСАНИЕ ПРОЕКТА» выше) как эталонный источник истины на весь хакатон —
    команда должна иметь возможность свериться с оригиналом текста задания в любой момент, не
    полагаясь на пересказ в других файлах.

Не сокращай и не упрощай содержание — эти файлы читает и человек (для координации), и,
возможно, технический эксперт/AI-судья на этапе технической проверки (вспомогательный
инструмент предварительного анализа, финальное решение всё равно принимают люди).
