# Протокол передачи модуля (handover)

Ситуация: участник закончил свой модуль раньше остальных и хочет помочь другому модулю —
со своего ноутбука и своего агента (Claude Code или Codex). Участники физически на разных
устройствах на площадке, поэтому `git worktree` не подходит (это механизм для параллельных
сессий ОДНОГО человека на ОДНОЙ машине) — используем обычные git-ветки push/pull.

Цель: сделать это без гонки коммитов и без путаницы, кто сейчас чем занят.

## Шаги

1. **Проверить `docs/task-board.md`.** Убедиться, что задача, к которой хотите присоединиться,
   свободна или что владелец модуля не против помощи именно сейчас.

2. **Владелец модуля коммитит и пушит текущее состояние.** Прежде чем кто-то ещё зайдёт в
   ветку, текущая работа должна быть закоммичена (даже промежуточная, с пометкой
   `# STUB` при необходимости) и запушена в удалённую ветку модуля (например, `backend`).

3. **Сообщить команде в чат:** кто, к какому модулю присоединяется, с какого часа.

4. **Обновить `docs/task-board.md`:** добавить строку с новым участником, статусом
   `in-progress`, и указать, что сейчас в модуле два человека.

5. **Договориться, кто пишет код прямо сейчас.** Пока в одной ветке физически работают два
   агента на двух машинах — правило простое: **коммитит в ветку только тот, кто в данный
   момент активно пишет**. Второй участник либо:
   - ждёт, пока первый закоммитит и запушит, затем делает `git pull` и продолжает — классическая
     передача эстафеты; или
   - берёт отдельную, явно не пересекающуюся часть задачи (например, отдельный эндпоинт или
     отдельный файл) и коммитит в ту же ветку только после `git pull` перед своим коммитом,
     чтобы не создавать конфликт.

   Одновременные коммиты в одну ветку без `pull` перед каждым — запрещены, это гарантированный
   конфликт мерджа в условиях ограниченного времени.

6. **Перед началом работы — обязательный `git pull`.** Новый участник модуля обязан подтянуть
   актуальное состояние ветки перед тем, как начинать писать код, иначе он работает поверх
   устаревшей версии.

7. **Прочитать контекст модуля перед началом:** свою строку(и) в `docs/progress.md` за
   предыдущие часы этого модуля, актуальный `docs/api-contract.md` и `docs/db-schema.md`, и
   код, который уже есть в папке модуля. Не начинать писать код, не поняв, что уже сделано.

8. **По окончании часа — обновить `docs/progress.md`** и отметить смену модуля в таблице
   «Смены модуля» внизу этого файла (кто, откуда, куда, почему).

9. **Если помощь больше не нужна** (участник возвращается к своему исходному модулю или
   освобождается) — обновить `docs/task-board.md` ещё раз, убрать себя из активных по чужому
   модулю.

## Чего не делать

- Не работать в одной ветке без координации «кто сейчас коммитит» — потеряете время на
  разрешение конфликтов, которого и так мало.
- Не создавать отдельный, несинхронизированный репозиторий/форк для «помощи» — вся разработка
  обязана быть видна в едином репозитории команды (см. `CLAUDE.md`/`AGENTS.md` п.3) — это
  требование Положения, а не пожелание.
- Не забывать `docs/task-board.md` — если статус не обновлён, третий участник может случайно
  начать делать то же самое.
