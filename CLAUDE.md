# CLAUDE.md — контракт команды для Claude Code

Этот файл автоматически читается Claude Code в начале каждой сессии в этом репозитории.
Он — общий контракт для всех участников команды, работающих параллельно на разных ноутбуках.
Эквивалент для OpenAI Codex — файл `AGENTS.md` (те же правила).

## 0. Обязательно прочитать первым делом

Прежде чем писать любой код: прочитать полный текст официального ТЗ (Технического задания)
выбранной задачи хакатона, включая её собственные критерии оценки. **У каждой из 30 задач
хакатона — своё полноценное ТЗ**; общей «идеи проекта от команды» больше нет — есть кейс,
который объявляют после старта, и решение должно соответствовать именно его требованиям.
Если критерии из ТЗ задачи противоречат общим формулировкам в этом файле — приоритет у ТЗ задачи.

Также прочитать:
- `/docs/api-contract.md` и `/docs/db-schema.md` — источник истины по интерфейсам между модулями
- `/docs/plan.md` — план на 5 часов соревновательной части
- `/docs/task-board.md` — кто сейчас чем занят (обновляется по ходу)

## 2. Критерии оценки — два разных этапа, не путать

**Технический отбор (до Demo Day):** оценивают технические эксперты (при поддержке
вспомогательных AI-судей, используемых только для предварительного анализа/ранжирования —
финальное решение принимают люди) по критериям, утверждённым для конкретной задачи. Эти
критерии могут отличаться от задачи к задаче — их нужно прочитать в ТЗ выбранной задачи и
вписать сюда после объявления кейса:

**Demo Day (только для финалистов):** единая для ВСЕХ задач таблица (по последней проверенной
версии Положения):

|---|---|
| Ценность решения | 25 |
| Результат и качество решения | 20 |
| Инновационность | 15 |

## 3. Критично для допуска — не нарушать

- **Репозиторий.** Работаем только в этом репозитории (создан Организатором через
  edu.astanahub.com). Никаких параллельных личных репозиториев с «настоящим» кодом — история
  разработки должна быть видна здесь.
- **Подтверждённый результат каждый отчётный час.** Отсутствие подтверждённого промежуточного
  результата за любой отчётный час — основание для дисквалификации команды. Практически:
  **в конце каждого часа должен быть коммит** — рабочий код и/или заполненная строка в
  `docs/progress.md`. Это не бюрократия, это прямая защита команды. Агент обязан следить за этим
  сам (см. п.6 и технический Stop-hook, который блокирует завершение хода без этого).
- **Воспроизводимость.** Каждый коммит должен оставлять проект в состоянии, которое реально
  запускается по инструкциям README на чистом клоне. Не оставлять код в сломанном состоянии
  дольше, чем на текущий рабочий отрезок.
- **Раскрытие вклада третьих лиц.** Если что-то сгенерировано ИИ или взято из готового
  шаблона — это нормально и разрешено (см. п.4), но не выдавать заранее подготовленную
  инфраструктуру за часть «основного функционала» в описании решения.

## 4. Что можно готовить заранее, а что — нет

Разрешено заранее готовить: инфраструктуру, инструменты, шаблоны, скрипты автоматизации —
при условии, что это не готовый продукт и не основная (профильная) часть решаемой задачи.
Файлы `.claude/hooks/check-progress-and-tests.sh`, `.claude/settings.json`,
`.claude/agents/supervisor.md`, структура `docs/*.md` — это именно такая инфраструктура, не
продукт. Она уже была подготовлена до начала соревновательной части.

**Основной функционал, специфичный для выбранной задачи** (бизнес-логика, обработка данных
кейса, вызовы OpenAI API под конкретный сценарий, расчётная/агентная логика решения) —
должен быть создан именно во время соревновательной части. Это фиксируется по часам в
`docs/progress.md` — это и есть доказательство для судей, что решение не «домашняя заготовка».

## 5. Разделение по модулям — гибкое, не жёсткое

Базовое разделение (может меняться по ходу — см. п.7 «Смена модуля»):

- **`/backend`** — владелец: [ИМЯ]. Бизнес-логика, расчётные/риск-модели, оркестрация вызовов
  OpenAI API, REST API endpoints (API теперь часть backend, отдельного модуля api-ui нет).
- **`/data`** — владелец: [ИМЯ]. Сбор, подготовка и загрузка данных (тестовый датасет / открытые
  данные с указанием источника / данные для ручного демо-ввода). Не пишет бизнес-логику backend.
- **`/ui`** — владелец: [ИМЯ]. Только фронтенд/интерфейс демо — вызывает эндпоинты `/backend`
  по контракту, свою логику API не пишет и не дублирует backend.

## 6. Контракт — источник истины

`/docs/api-contract.md` (эндпоинты, форматы запросов/ответов, ошибки) и `/docs/db-schema.md`
(схема данных) — единственный источник истины о том, как модули договариваются между собой.
Правило изменения: обсудили → обновили контракт → только потом меняем код. Менять код под
контракт, который не обновлён в доке, — запрещено, даже если «так быстрее».

## 7. Смена модуля / помощь другому участнику (handover)

Если участник закончил свой модуль раньше остальных, он может переключиться и помогать
другому модулю — **со своего ноутбука и своего агента**, не через общий воркспейс (участники
физически на разных устройствах, поэтому `git worktree` не подходит — используем ветки).
Порядок действий описан пошагово в `docs/handover-protocol.md` — прочитать перед переключением.
Коротко: текущий владелец модуля пушит ветку и предупреждает команду → doc `docs/task-board.md`
обновляется (кто сейчас на каком модуле) → пока два агента работают в одной ветке одновременно,
владелец, который НЕ пишет код прямо сейчас, не коммитит в эту ветку, чтобы избежать гонки
коммитов → перед сменой роли — обязательно `git pull` свежей ветки.

Всегда перед переключением проверить `docs/task-board.md` — не занялся ли уже кто-то этой
задачей.

## 8. Запрет имитации (моков и заглушек)

Запрещено в путях основного сценария на момент коммита в `main`:
- Захардкоженные «ответы» вместо реальных вызовов OpenAI API / реальной обработки данных
- Оставленные `TODO` / `NotImplementedError` / функции, которые ничего не делают и возвращают
  фиктивный успешный результат
- `try/except`, которые проглатывают ошибку и возвращают фейковый «success»
- Функции, игнорирующие свои входные аргументы

Легитимная временная заглушка (например, пока не готова соседняя часть) помечается
комментарием `# STUB: заменить перед мержем` и обязательно должна быть заменена до
финального коммита.

## 9. Объяснение после каждой задачи — автоматически

После любого значимого изменения кода агент САМ, без просьбы, заполняет свою строку в
`docs/progress.md` за текущий час: что сделано + как это работает простыми словами (не просто
«добавил функцию X», а что она реально делает и почему). Это напрямую служит требованию
Положения о подтверждённом результате за каждый отчётный час (см. п.3) — и пригодится на
вопросах судей на Demo Day.

Claude Code технически принуждает это через Stop-hook
(`.claude/hooks/check-progress-and-tests.sh`) — он блокирует завершение хода, если код менялся,
а `docs/progress.md` — нет. У Codex такого технического механизма нет — участник на Codex
обязан делать это вручную, без исключений (см. `AGENTS.md`).

## 10. Тесты именно этого этапа

Каждый модуль (`/backend`, `/data`, `/ui`) содержит исполняемый `./test.sh`, проверяющий
работоспособность именно того, что только что сделано (конкретная функция/эндпоинт на
конкретном входе → ожидаемый результат) — это НЕ то же самое, что `/code-review` (проверяет
стиль и логику по диффу) и НЕ то же самое, что проверка `supervisor`-агента (проверяет
соответствие контракту и признаки имитации на объединённой ветке). Нужны все три уровня.

## 11. Definition of Done (перед коммитом в общую ветку)

1. Обновить `./test.sh` модуля под новую функциональность и прогнать его
2. `/code-review` изменений
3. Явно проверить себя на моки/заглушки по чек-листу п.8
4. Ручная проверка минимум на 2 разных входных данных
5. Проверка соответствия контракту через `supervisor`-агента
6. Заполнить свою строку в `docs/progress.md` (что сделано + как работает)
7. Коммит

## 12. Технический риск — не забывать

- Не пытаться обучать ML-модель в рамках 5 часов — только простая математика/правила +
  вызовы OpenAI API. На обучение модели времени физически нет.
- В конце окна — обязательная проверка: чистый клон репозитория → запуск строго по README →
  без ручных правок. Несоответствие этому — риск недопуска к дальнейшему отбору.

## 13. Регулярная синхронизация работы команды

Перед каждой задачей, перед коммитом/пушем и каждые 10–15 минут активной длительной работы:
проверить `git status`, выполнить `git fetch origin`, прочитать новые коммиты соседних веток
и их изменения в `docs/task-board.md`, `docs/progress.md` и контрактах.
Не считать локальную копию этих документов полной картиной работы команды без `fetch`.

Если рабочее дерево чистое, обновить свою ветку командой `git pull --ff-only origin <своя-ветка>`.
При незакоммиченных изменениях сначала выполнить только `fetch` и просмотр удалённых версий;
свои правки сохраняются. При расхождении истории или конфликте остановиться и показать
проблему пользователю. Не использовать force-push или сброс файлов для синхронизации.

Общие документы приходят из `main` отдельным слиянием после сохранения своей работы коммитом.
Код чужого модуля читать в его ветке, не переносить автоматически в свою.
Подробные команды и порядок учёта чужих изменений — `docs/repository-sync.md`.
