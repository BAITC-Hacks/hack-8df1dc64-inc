## Первая реализация B1: проверка запроса и погодного пакета

Предлагаемый стек первого этапа: Python, стандартная библиотека и `unittest`.
Проверка реализуется как функция backend до подключения HTTP и внешних сервисов.
Время на B1: 30–45 минут после согласования форматов.

### Запрос прогноза

| Поле | Тип | Правило |
|---|---|---|
| `as_of` | string, ISO 8601 с часовым поясом | Момент исторического запуска, ровный час |
| `horizon_hours` | integer | От 24 до 48 включительно |
| `turbine_ids` | array of string | Непустой список без повторов: `turbine_1`, `turbine_2` |

Все сравнения времени выполняются после перевода в UTC. Вход без часового пояса отклоняется.
Часовой пояс сырых исторических файлов пока неизвестен: преобразование нельзя угадывать.

Предлагаемая сетка: `as_of + 1 час`, ..., `as_of + horizon_hours часов`.
Каждая метка обозначает конец часового интервала. Это соглашение требует подтверждения
по данным организатора; само ТЗ не определяет начало или конец интервала.

### Погодный пакет от модуля data

| Поле | Тип | Правило |
|---|---|---|
| `source` | string | Непустой идентификатор источника |
| `run_id` | string | Непустой идентификатор выпуска прогноза |
| `issued_at` | string, ISO 8601 с часовым поясом | Время выпуска модели |
| `available_at` | string, ISO 8601 с часовым поясом | Когда выпуск стал доступен пользователю источника |
| `availability_evidence` | string | Ссылка или описание основания для `available_at` |
| `wind_height_m` | number | Положительная высота, к которой относится скорость ветра |
| `points` | array | Точки на полной запрошенной сетке для каждой выбранной турбины |

Поля точки: `turbine_id`, `valid_at` (время с часовым поясом), `wind_speed_ms`
(конечное число >= 0), `temperature_c` (конечное число).

Условия: `issued_at <= available_at <= as_of`. Время скачивания архива сегодня не является
временем его исторической доступности. Одного `issued_at` недостаточно: выпуск мог появиться
в источнике позже запуска модели. Backend проверяет согласованность метаданных; достоверность
исторической доступности должна подтверждаться источником и адаптером data.

Один пакет содержит один выпуск. Адаптер data выбирает выпуск, покрывающий всю сетку;
автоматически смешивать разные выпуски на этом этапе не предлагается.
Пропуски, дубли пар `(turbine_id, valid_at)`, неизвестные турбины и лишние часы отклоняются.
Фактическая погода и переанализ не подставляются вместо архивного прогноза.

### Результат проверки

Успех: проверенные значения запроса и пакета с датами в UTC.
Ошибка: структурированная причина с `code`, `field`, `message`.
Коды: `INVALID_REQUEST`, `INVALID_WEATHER`, `WEATHER_NOT_AVAILABLE`,
`INCOMPLETE_WEATHER_GRID`. Проверка не вычисляет и не возвращает фиктивную выработку.

## Последующие этапы после B1

1. Проверить реальный формат истории, единицы мощности, шкалу нормализации, часовой пояс,
   трактовку часовой метки и доступность исторических наблюдений.
2. Зафиксировать контракт истории и результата прогноза; выбрать расчёт по историческим данным.
3. Реализовать расчёт и ежедневный исторический прогон февраля с разделением истории и теста.
4. Добавить агентный цикл и HTTP API по отдельно зафиксированному контракту;
   затем проверить обновление данных и повторный расчёт.

Выбор модели, источник архивной погоды и итоговые API-эндпоинты сейчас не утверждены.
Оценка этих этапов зависит от формата истории и доступности архивов.

## Проверки B1

- Полный пакет для 24 часов и одной турбины проходит.
- Полный пакет для 48 часов и двух турбин проходит; равные моменты с разными смещениями
  часового пояса сравниваются одинаково.
- Выпуск до `as_of`, опубликованный после `as_of`, отклоняется.
- `available_at == as_of` разрешено; `issued_at > available_at` отклоняется.
- Пропущенный час, повтор точки, лишний час и чужая турбина отклоняются.
- Даты без часового пояса, дробный горизонт, булевы значения вместо чисел,
  бесконечность, NaN и отрицательная скорость ветра отклоняются.

`backend/test.sh` будет запускать эти исполняемые тесты вместе с реализацией B1.
Дополнительно выполняются два ручных сценария: корректный пакет и поздно опубликованный выпуск.
Тестовые пакеты будут явно искусственными данными для проверки правил, без заявлений о
точности прогноза или наличии реального погодного архива.
